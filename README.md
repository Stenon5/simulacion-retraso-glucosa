# glucose-delay-simulation

Can the delay between blood glucose and tissue glucose be estimated from two
optical depths alone, with no blood sample, and does knowing it make a
hypoglycemia alarm fire earlier?

and the test skeletons are committed. The simulation itself is not written.
`results/` is empty and no figure has been produced. Numbers appear in this

## Not a medical device

This repository is a simulation study. It is **not a medical device**, it does
**not diagnose, treat or monitor any condition**, and it must **not be used to
make any decision about anyone's health**. There is no hardware, no sensor, no
measurement on a person and no clinical validation. Every number this code
will ever produce comes from synthetic data generated by the model described
in `docs/spec.md`.

## The question, stated so it can fail

Two sensing depths see the same blood glucose signal through two different
first order diffusion delays. The claim under test is that those two delayed
signals are enough to identify both delays, without ever measuring blood
glucose.

Pass and fail thresholds are fixed in [`thresholds.yaml`](thresholds.yaml),
committed before the code that checks them exists. They are not edited after
seeing a result. An amendment goes in a new file.

One disclosure. The thresholds were chosen after an earlier exploratory run
(2026-10-16) whose scripts are not in this repository. This repository is the
replication, so the thresholds are fixed before the replication and not
before the idea was first tried.

## What this is NOT

* Not a device, not a prototype, not hardware.
* Not a validation of any sensing technology. It assumes a sensor exists and
  asks what noise level that sensor would have to reach for the method to be
  worth anything.
* Not evidence of accuracy in a person. Synthetic data generated by the same
  model the estimator assumes is a verification that the estimator solves its
  own equations. It is not a validation.

That last point is the main limitation of the whole design and it is why
`docs/misspecification-sweeps.md` exists.

## Why a negative result is the useful outcome

The method only helps if the sensor is quiet enough. If the required noise per
reading is below what optical sensing has been shown to reach, the honest
conclusion is a bound: the algorithm is not the bottleneck, the hardware is.
That bound is the deliverable, whether or not it is encouraging.

For reference on the hardware side, an in vitro study using a quantum cascade
laser reported a noise equivalent glucose concentration of 4 mg/dL at an
average power of 1.8 mW with an integration time of 50 s
(Vrančić C et al., *Analyst* 2011, 136:1192,
DOI [10.1039/C0AN00537A](https://doi.org/10.1039/C0AN00537A)). That is an in
vitro figure for one setup. No equivalent has been shown on a person.

## Reporting rule

Bias is never reported alone. Every bias is reported next to the standard
deviation across runs, per scenario. A mean bias that looks small can sit on
top of a spread several times its size, and a single averaged number hides
that. This rule is in `thresholds.yaml` and applies to the README, the report
and any figure.

## Limitations

Written before this repository produces any result, because they follow from the design.

* **Circularity.** Synthetic data is generated by the same first order
  diffusion model the estimator assumes. Reproducing the delay under those
  conditions verifies the estimator. It does not validate the model against a
  body.
* **Constant delay.** The delay is held fixed. Perfusion changes with
  exercise, temperature and position.
* **White noise.** No drift, and no correlation between the two depths. On
  real optical sensors slow drift tends to dominate the error, and two depths
  of the same instrument would share part of their noise.
* **One synthetic day.** A short synthetic record with one hypoglycemic
  excursion is not a day of living with diabetes.
* **The reported delay in people varies.** Published estimates of the blood to
  interstitial delay are not a single number, so a single true value in a
  simulation is a convenience, not a fact about anyone.
* **No sensor.** The noise level is an input, not something measured.

## What failed

Real attempts, with what each one taught. Full entries, including the numbers
once they can be reproduced by the code in this repository, are in
[`AGENT_LOG.md`](AGENT_LOG.md).

* Regression on the derivatives of the two signals returned a negative time
  constant, which is physically impossible. Differentiating a noisy signal
  moved the noise into the design matrix.
* The integral form fixed the sign and recovered the difference between the
  two delays, but pulled both of them down. The information that separates one
  delay from the other lives in the small difference between the two readings,
  and noise dilutes exactly that.
* Correcting for error in the variables addressed that bias. This is the
  version `docs/spec.md` describes.

## Next step, no hardware needed

Before anything else, the misspecification sweeps in
[`docs/misspecification-sweeps.md`](docs/misspecification-sweeps.md): variable
delay, noise correlated between depths, sensor drift, and kinetics that are
not first order. The point is to find where the estimator breaks and publish
that.

Only after that is there any value in richer glucose curves from an open
source type 1 diabetes simulator. A candidate is simglucose
(<https://github.com/jxx123/simglucose>, MIT licensed), whose README describes
it as a Python implementation of the UVa/Padova simulator, 2008 version, for
research use. That is a description of the package, not a claim about
regulatory status, and the package being open source does not remove the
circularity problem by itself.
